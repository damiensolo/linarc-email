# Decisions

Standing decisions inherited from the first module (`linarc-prototypes`, Prequalification), kept with their original IDs because the rules in `CLAUDE.md` and `5-ui-patterns.md` cite them. Module-specific decisions of that module (D-13's tool list, D-16's five dimensions, D-23, D-28, D-31, D-32) stayed there. Add this app's decisions below, continuing from D-33.

| # | Date | Decision | Why | Rejected alternative |
|---|---|---|---|---|
| D-01 | 2026-10-06 | Use the design system **from source** through Vite aliases, not the published package | Library fixes show up immediately; no publish cycle while prototyping | Install the package from the registry: slow feedback, and needs tokens |
| D-02 | 2026-10-06 | Vue 2.7 Options API, plain JS in prototypes | It's the library's stack; its components won't run on Vue 3 | Vue 3 / `<script setup>` |
| D-03 | 2026-10-06 | Load the library's `global.css` and rebind `body` to tokens | Match production styling while keeping dark mode working | Tokens only (diverges from production), or `global.css` as-is (breaks dark mode) |
| D-04 | 2026-10-06 | Keep the library's catch-all safelist (8 MB CSS) | Components build class names at runtime; trimming would silently drop styles | A sandbox-only safelist override |
| D-05 | 2026-10-06 | Always-on rules in CLAUDE.md, the workflows as skills, Cursor rule as a pointer | One source of truth; a workflow loads only when needed | A single long `.cursorrules` copied per tool |
| D-06 | 2026-10-06 | Prototyping may fix or add to the library: fix in place, fork, or create a new component, always flagged (`PROTOTYPE-CHANGE`) and logged | Prototypes shouldn't be blocked by library gaps, and every change stays reviewable for an MR | Never touch the library (blocks work), or hand-build lookalikes (drift) |
| D-07 | 2026-10-06 | Verification uses puppeteer-core with an installed Chromium browser (Edge by default; Chrome via `EDGE_PATH` when Edge won't launch, F-041) | Exact viewports, full-page captures, real console capture, no browser download | Edge headless CLI (wrong viewport, F-010) |
| D-08 | 2026-10-06 | Responsive from 390px to 1440px+, verified at 1440, 1024 and 390 | Product requirement | Desktop-only |
| D-09 | 2026-10-06, settled 2026-10-13 | Hosting on Vercel as a **prebuilt upload**: build locally, upload `dist/` only (`yarn deploy`) | Vercel can't build the app (the library is compiled from a private sibling checkout); a prebuilt upload needs no monorepo or submodule | Git-connected builds (fail without the library), a monorepo (too much change for a sandbox) |
| D-11 | 2026-10-06, superseded by D-14 | When Figma and live library defaults disagreed, code won and Figma was aligned to it | The components were live in production | — |
| D-12 | 2026-10-06 | Components missing from code are added to the system on both sides (Figma variant + library code + Code Connect), not kept in prototypes | Reuse, and correct Dev Mode snippets | Prototype-local workarounds |
| D-13 | 2026-10-07 | **A module is one self-contained area**: a module tile in the top nav, tools in the strip, one side-nav rail per tool; settings live under the module's own Configure tool; one shell (`AppShell`) for every screen of the module | Matches how the product's modules end with Configure; new Figma variants only, no edits to other modules | Spreading a module's screens across existing modules' tools |
| D-14 | 2026-10-07 | **Figma is the source of truth.** When Figma and code disagree, code is changed to match Figma and logged (P-NNN); obvious Figma slips are kept as drawn and flagged for design | Stated by the user. Supersedes D-11 | Code wins by default |
| D-15 | 2026-10-08 | **Candidate stage for components missing on both sides.** Proposal doc (`docs/components/<Name>.md`) → built in `src/candidates/<Name>/` and used by a prototype → drawn in Figma with variables bound for a design iteration → promoted into the library with stories, README, `.figma.js` and a P-row → candidate deleted | Putting them straight into the library skips the design iteration; keeping them in a prototype makes them lookalikes with no path back into the system | Straight into `componentsV2`; prototype-local widgets; Figma first (blocks the prototype on design time) |
| D-16 | 2026-10-08 | **Status is a set of independent dimensions**, each with user-facing labels and a tone per value, implemented once in `src/modules/app/status.js` and documented in the module's `status-model.md` | One flat enum can't express "approved, renewal under review"; one shared vocabulary keeps every screen consistent and makes a status component possible | A flat enum; per-screen status strings |
| D-17 | 2026-10-09 | **Visual hierarchy rules for module screens** (references: Linear, Mercury, Airwallex): one container level per view, hairlines instead of boxes, colour only on the primary action and on states that ask for action, one signal per status (check *or* word *or* chip), label-only buttons unless the icon carries meaning the label doesn't, a fixed footer for step navigation | The first build nested cards three deep and put a dot, coloured text and a chip on every status; the user asked for a minimal, intentional hierarchy | Per-screen taste; the library card defaults everywhere |
| D-18 | 2026-10-09 | **Create flows are full-page create screens, not modals**: module nav stays, Title Bar / Workflow heads the page, the form fills the content area, step navigation sits in a fixed bottom panel. Alternatives worth comparing are a second prototype slug (`<slug>-<variant>`) sharing state and components | It is the app's existing pattern (RFI create) with library components behind it; a modal hides the page context and gains nothing for a multi-step form | A ModalV2 wizard (kept as a version B for comparison) |
| D-19 | 2026-10-09 | **Create-screen layout: centred form column with an aligned footer.** Stepper and form in a centred column; the fixed bottom panel spans the content area and its buttons align to the same column. UI and pattern decisions are consolidated in `5-ui-patterns.md` | A left-aligned column left ~40% of a 1440 screen empty and made the footer's buttons look misplaced | Left column (RFI layout without its panel); full-width form |
| D-20 | 2026-10-09 | **Wide-form column is 56rem (896px)**, `max-w-4xl`; 48rem (`max-w-3xl`) for short single-column forms | Guidance puts the standard form maximum near 720px but allows wider for tabular data; 56rem is the next step on the scale | An arbitrary width (disallowed); full width |
| D-22 | 2026-10-10 | **The Figma reference for a module is an app map**, not loose frames: one page per module in the Documentation file, one section per level, editable library instances with a numbered label, arrows (solid blue = navigation, dashed orange = state change, grey = back / cancel), a tinted outline on the element clicked. Light mode only; dark mode is verified in code | One page shows how the screens connect; design reviews there | Loose Light / Dark frames per screen |
| D-24 | 2026-10-10 | **Screens never blank: in-document navigation, and loading shown only in the region that is loading.** `router.go()` pushes history and App.vue swaps the screen. Data loads through `createLoad` + `LoadRegion` / `LoadStatus`: nothing for 200ms, then a skeleton in the final layout (first load) or an inline "Updating…" with the content kept (refresh); "Still loading…" + Cancel after 5s; error + Retry; latest request wins; aria-busy and polite announcements; static under reduced motion. Tables use DataGrid `loading` (P-034). Rules in `5-ui-patterns.md` §6 | Clicking between screens blanked the whole app (a full reload on every link, F-057); loading had no agreed shape | Full-screen spinners; `location.assign` links |
| D-25 | 2026-10-11 | **Detail and create screens use the comfortable title bar with a contained back button.** Title Bar / Workflow `Size=Comfortable` (64px) and Header Tool Icons `Type=Back`; in code `AppShell header-size="comfortable"` + `HeaderToolIcon type="back"` (P-038). List screens keep the 48px Title Bar / Page | People who don't recognise a bare chevron can't find their way back | A labelled "Back" button; a breadcrumb (no Figma component) |
| D-26 | 2026-10-11 | **Data entry is left-aligned and sized to its value; only read-only numbers in tables are right-aligned.** Rules in `5-ui-patterns.md` §7 | Right-aligned values in wide inputs sat far from their labels; Figma's Input Field is left-aligned for every type | Keep right alignment and narrow every input |
| D-27 | 2026-10-11 | **The sandbox has a record picker.** A screen that takes a record id in the hash declares `prototype.records`; App.vue shows a second select and opens the chosen record | Many records are otherwise reachable only by typing hashes; the picker is outside the product, so no prototype-only UI inside a screen | A record switcher inside the screen; a demo index page |
| D-29 | 2026-10-11 | **The module runs end to end on a demo session.** `src/modules/session.js` holds everything a person changes, overlays the static mock data at start (imported in `main.js`), persists to sessionStorage; the sandbox's Reset demo data clears it | A demo must complete the workflow with the state changes visible on every screen | Per-screen local state (changes vanish on the next screen) |
| D-30 | 2026-10-12 | **List screens filter through the grid's Filter panel, with quick filters; a screen's segmented views stay and are cross-linked with it.** No count line or Clear link above the table. Rules in `5-ui-patterns.md` §8 | Filter selects above a table proved awkward; the grid already has a panel with a count badge | Selects and chips above the table |
| D-33 | 2026-10-15 | **New apps start from `linarc-prototype-base`.** The template carries the wiring, sandbox, shell, loading pattern, agent instructions, checks and docs; module-specific code stays in each app; improvements that apply to every app go back to the template | The first module's first days went on wiring and its reviews repeated the same conventions | Copying the last app and deleting (module code leaks through); a monorepo (too much change) |
| D-34 | 2026-10-16 | **Contextual create and supporting detail may overlay the page.** Narrows D-18 to *primary* multi-step / long create flows (still full-page). A create started from context (Compose Email from a Drawing/RFI, Promote Email to Record) opens in a **SlideOverPanel** (candidate) or a **compact ModalV2**; supporting detail opens in `AppShell right-panel` when persistent, or a SlideOverPanel (`size="md"`, 560px) when triggered on demand over a canvas or table. `5-ui-patterns.md` §1 | Keeps the underlying canvas or thread visible for spatial reference | A full-page create screen for every create; reusing the right panel for all supporting detail (the old "no drawer" rule) |
| D-35 | 2026-10-16 | **Correspondence is a cross-tool capability plus a central log**, not an isolated module: compose from Drawings, RFIs, Submittals and COs; one project Email screen for triage; the record Email tab (naming per D-40). The MVP shows it inside Drawings and RFIs **stand-in** screens (`correspondence-context-dwg`, `-rfi`) | People start messages from the record they are looking at; a standalone inbox hides the main entry point | Standalone module only |
| D-36 | 2026-10-16, settled the same day | **Recipient entry needs a typed email and inline guest creation inside the compose panel** (name and company pre-filled from the address, role select, saved to the session); never a modal over the panel. **Settled (Q-02):** an InputV2 *Add by email* row under the recipients select opens the inline guest form and creates a guest user; `SelectV2 multiple` and P-041 are unchanged. The first proposal (`allow-create` on the select) needed typing that P-041 removed on 2026-10-12 | A consultant not yet in the directory is the common case for a first message; leaving the panel to set them up loses the drawing context | Directory-first setup; a ModalV2 stacked on the panel |
| D-37 | 2026-10-16 | **Promote email to a record happens in place**: SlideOverPanel `md` beside the thread with the source message highlighted (default); the compact ModalV2 variant (`correspondence-thread-modal`) is **deferred** (settled 2026-10-16): D-34 already chose the panel and the product has no modal precedent; build it only if sessions show trouble with the panel | Five pre-filled fields don't need a page; the PM must see the subcontractor's wording while confirming the question. | D-39 | 2026-10-16 | **The external portal shows nothing internal and shows the link's state.** Never internal notes, cost fields or other recipients' audit rows; the page states valid / expired / revoked and offers *Send me a new link* when expired. | D-40 | 2026-10-16 | **Correspondence upgrades the platform's existing Email, it does not replace it.** The record Email tab (RFIs, Submittals, COs) and the project Email screen (Project › Communication › Email) keep every field and behaviour they have today (From, To = guest users, CC, prefilled subject, rich text, attachments from device or project files, record PDF, per-recipient delivery status, auto-threaded replies, reply notification, no sending from a closed record); the MVP adds on top: compose from a drawing with a revision pin, inline guest creation, large files by link, triage states and Response due, Unmatched inbound mail with Link to record, internal notes, Promote to RFI, Link opened / Files downloaded. Parity table: `correspondence/00-plan.md` §0 | The help centre shows the plumbing already exists; clients would read a parallel "Correspondence" system as a regression and a rename | A new Inbox tool beside Email; renaming Email to Correspondence |
| D-41 | 2026-10-16 | **Visibility model for Email** (table in `correspondence/spec.md` §3): internal team members see every project thread; Confidential threads only participants and PMs; guests only the threads they are on; internal notes and cost never leave the company; To and CC visible to each other as in ordinary mail; only internal roles promote or link; the secure link page shows one thread and the recipient's own delivery state (D-39) | Stated by the user as "the recommended best practice"; the record is shared, mail is not hidden beyond what mail itself hides, and anything internal must be unmistakably internal | Participants-only visibility for internal users (hides the record); company-wide visibility for guests |
| D-42 | 2026-10-16 | **Hybrid inbox-plus-record model, with notifications.** PMs read and answer everyday mail in Outlook or Gmail; Linarc holds the project record and the formal workflows. Every outbound mail and notification is answerable by reply (the token keeps the thread); the project address is shown wherever mail is composed or forwarded; three notifications are added to today's preferences (Needs action once, Overdue at the deadline then a daily digest, Delivery failed at once), each answerable by reply and carrying one link. The Email screen is the record and triage view, not the PM's inbox. An Outlook or Gmail add-in is the follow-up | Stated by the user: Procore, Autodesk Construction Cloud and Newforma support this model (a conclusion from their supported workflows, not a measured usage share); designing as if the platform replaces the inbox would fail silently | Platform inbox as the PM's primary mailbox; no notifications beyond today's reply alert |
| D-43 | 2026-10-16 | **Secure link lifecycle:** valid 30 days from sending; revocable by the sender from the thread; an expired page offers *Send me a new link* to the same address; opening and downloading are recorded; a reply from the page threads like a mailed reply and is copied to the recipient's own mailbox | The user accepted the spec's proposal; a dead end on an expired link and a reply that exists only in Linarc would both break the hybrid model (D-42) | Permanent links; identity verification beyond the address; portal-only replies |
| D-44 | 2026-10-16 | **AI content follows industry practice:** labelled with the AI chip and disclaimer until a person edits it; sourced by an evidence line and per-bullet trace; never sent or saved without a human action (Promote needs the Question field touched once); fails gracefully to a usable screen; has a feedback link; is generated only from content the viewer may see (D-41). Rules in `correspondence/spec.md` §6.2 | Stated by the user: best practice. Matches the common guidance for AI in products (disclose, keep the person in control, show provenance, fail safe, collect feedback) and the §9 pattern already in the system | AI text sent unedited; unlabelled pre-fill; summaries that silently disappear on failure |
| D-45 | 2026-10-18 | **Attachments are tiles that open in a full-screen viewer.** A message's files show as the library's `AttachmentThumbnail` (Figma Image Links Thumbnail, P-048) with a name / size caption; the tile opens the `FileViewer` candidate over the screen (image zoom, PDF in the browser's viewer, video, previous / next through the message's files, Download, *No preview* for other types). | D-46 | 2026-10-19 | **Compose To lists the people already in the system; new people are added as guest users explicitly.** To offers everyone in the project directory (team and existing guests) except the sender, suggested first; the row under it is *Add a guest user* (heading; one line, *Not in the directory yet? | D-47 | 2026-10-19 | **Compose recipients are RecipientField rows: To, Cc, and Bcc behind a toggle.** Typeahead over the project directory (suggested first), chips that say who each recipient is: amber for any domain outside the company's (the team's domains), red for an invalid address, neutral for the team; Enter / Tab / comma / paste / blur commit; Backspace cascade; double-click edits; chips drag between rows or move from their menu.
